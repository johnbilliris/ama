## Execution and acceptance procedure for every PR

Each numbered PR below is an independent work item and must retain its own
branch, dependency decision, validation evidence, commit, and push outcome.
Do not merge or close PRs as part of this request.

1. Record the remote head, merge base, changed files, requested version, and
   current `main` manifest/lock versions. Inspect upstream migration notes,
   supported runtimes, peer dependencies, native wheels/binaries, and the
   application's actual consumers. Historical research is a starting point,
   not current availability evidence.
2. Prepare the PR branch against the recorded current baseline without
   force-pushing. Resolve stale dependency changes by retaining newer protected
   versions; never replay an old lockfile wholesale. If the requested change
   is already satisfied, record that explicitly rather than manufacture an
   upgrade or downgrade. Preserve independent root, API, and agents locks.
3. Query the approved Microsoft package proxy for the exact candidate and
   required companions. Update only the relevant declaration and lock using
   pnpm 10.6.3 or uv 0.11.21. Preserve source restrictions, integrity records,
   security overrides, and unrelated dependency versions. A missing candidate
   or incompatible peer graph is a blocker, not permission for a substitute.
4. Build the applicable targets using
   `docker buildx bake -f docker-bake.json <targets>`. Every local target must
   remain `linux/arm64`. Run checks inside the local development container,
   and separately verify actual production-image dependency versions where
   ranged pip installation differs from locked development installation.
5. Compare candidate results with the unchanged baseline in the same
   environment. Execute the applicable checks below, recreate affected
   services using `docker compose up -d --no-build --wait`, and exercise
   browser/API behaviour. Record commands, exit codes, failures, skips, image
   IDs, and candidate commit. Do not describe service health alone as full
   regression, or mocked tests as live Azure validation.
6. Only mark an upgrade validated when all applicable checks pass. Review the
   exact diff, commit on that PR's branch, push normally to its existing remote
   branch, and verify the remote SHA. Preserve and report blocked work without
   claiming completion. Do not deploy, publish images, or dispatch production
   workflows.

## Regression selections

- **Python**: root unit, contract, integration, and simulation tests excluding
  explicitly live Azure/staging, measurement, e2e, load, and Locust markers;
  policy tests; affected package tests; Ruff on changed Python. Validate the
  affected lock using a locked install, not only the aggregate devcontainer
  environment. Exercise authentication, websocket/streaming, multipart,
  configuration, or serialization paths according to the PR.
- **Web**: domain typecheck/build, web ESLint, `tsc --noEmit`, Vitest including
  accessibility, production webpack build/postbuild, and Chromium/mobile
  incident commander, persona workspace, and decision-support acceptance tests.
  Use the existing Playwright configuration and its two-server harness.
- **Workflow**: parse changed YAML, run relevant `tests/devops` contracts and
  package-source policy checks, verify immutable upstream Action SHAs and
  declared runner/runtime requirements. Local Docker cannot prove hosted
  Actions execution; keep that limitation separate from application regression.
- **Application stack**: Cosmos schema seed succeeds; API, dispatcher,
  evacuation, ingestion, web, Redis, Azurite, and Cosmos reach healthy state.
  Exercise API liveness and frontend/API routing. Run browser acceptance rather
  than relying on health checks for user-visible functionality.
- **Python base image**: build and inspect the specific upgraded image,
  interpreter version and architecture; run dependency/import checks and
  affected behavioural tests with that interpreter, not Python 3.12 substitutes.
