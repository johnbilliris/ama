# Quickstart: LLM Evaluation Framework

**Feature**: 030-llm-eval-framework
**Audience**: an evaluation engineer running the framework end-to-end on the AMA platform for the first time.

This quickstart covers four flows: (1) provision the eval platform infra, (2) publish the seed disaster dataset, (3) trigger an ad-hoc multi-model run, (4) wire the release gate. Each flow ends with a verifiable outcome.

---

## Prerequisites

- Member of the `eval-author` Entra ID group.
- AMA platform `dev` environment is healthy (`pnpm -w lint`, `pnpm -w test`, `pytest -q` all green on `main`).
- Logged into Azure: `az login`, default subscription set, default location `australiaeast`.
- Permission to create `rg-ama-eval-dev` and deploy resources into it.
- Foundry account is provisioned by `eval-platform.bicep` into the eval RG (`rg-ama-eval-{env}`); the account name is published as the `foundryAccountName` deployment output. The carve-out list permits the v1 model regions.
- `gh auth status` shows write access to `johnbilliris/ama`.

## 1. Provision the eval platform (one-time per environment)

```pwsh
# from repo root
python scripts\run_llm_evaluation.py --stage provision --env dev
```

What this creates (all in `australiaeast`):

- Resource group `rg-ama-eval-dev` with required governance tags.
- Cosmos DB containers `eval_datasets`, `eval_runs`, `eval_metric_definitions`, `eval_audit` (public network allowed in dev; locked down outside dev).
- Storage account `stamaevaldev{uniq}` with **immutable** containers `datasets`, `runs`, `audit-archive` and a 7-year time-based retention policy (public network allowed in dev; locked down outside dev).
- Key Vault `kv-ama-eval-dev` for Foundry endpoint URLs and policy secrets (public network allowed in dev; locked down outside dev).
- Azure Container Registry `acramaevaldev{uniq}` containing the `eval-runner:dev` image built from `apps/eval-runner/Dockerfile`.
- Container Apps environment `cae-ama-eval-dev` and Container Apps Jobs `caj-eval-runner-dev` and `caj-eval-reconciler-dev` (cron every 30 min).
- Application Insights `appi-ama-eval-dev` linked to the eval Log Analytics workspace.
- Managed identity assigned `AcrPull`, `Cosmos DB Built-in Data Contributor`, `Storage Blob Data Contributor`, `Key Vault Secrets User`, and Foundry `Azure AI Developer` over the dev project.

**Verify**: `az containerapp job show -n caj-eval-runner-dev -g rg-ama-eval-dev --query "properties.provisioningState"` → `Succeeded`.

## 2. Publish the seed disaster dataset (`disaster-response-core@1.0.0`)

The seed corpus is generated by a controlled harness, then approved by safety reviewers (research D7/D8).

```pwsh
# 2a. Generate ~5,000 synthetic cases (writes drafts to packages/eval-dataset/cases/)
python packages/eval-dataset/generation/generate.py `
  --total 5000 `
  --distribution packages/eval-dataset/generation/distribution-v1.json `
  --provenance synthetic

# 2b. Validate locally (JSON Schema + Presidio + label invariants)
pytest tests/contract/test_eval_dataset_cases.py -q

# 2c. Open a PR — CODEOWNERS routes to @ama/safety-reviewers
gh pr create --title "eval: seed disaster-response-core v1.0.0" --body "..."
```

After the PR merges, the `eval-dataset-publish` workflow (`.github/workflows/eval-dataset-publish.yml`) runs and:

- Builds the canonical JSONL.
- Hashes it (SHA-256), uploads to `datasets/disaster-response-core/1.0.0/cases.jsonl` with the immutability policy applied (FR-009).
- Calls `POST /api/eval/datasets/disaster-response-core/versions` with the manifest.

For a development tenant that does not have the AMA API app registration installed, use
`python scripts\run_llm_evaluation.py --stage publish --env dev --skip-api-register` to upload the dataset artefacts
without calling the API registration endpoint.

**Verify**:

```pwsh
curl -H "Authorization: Bearer $TOKEN" `
  https://api.ama-dev.example/api/eval/datasets/disaster-response-core/versions/1.0.0
# → state: "published", caseCount >= 5000, contentHash: "sha256:..."
```

## 3. Trigger an ad-hoc three-model comparison run

```pwsh
$body = @{
  mode = "ad-hoc"
  datasetRef = @{ datasetId = "disaster-response-core"; version = "1.0.0" }
  modelRefs = @(
    @{ modelId = "openai/gpt-frontier"; version = "2026-04-01" }
    @{ modelId = "openai/gpt-mid";       version = "2026-04-01" }
    @{ modelId = "microsoft/phi-small";  version = "2026-04-01" }
  )
  metricSet = "disaster-core-v1"
  policyId = "default-eval-policy"
  policyVersion = "1.0.0"
} | ConvertTo-Json -Depth 6

$response = Invoke-RestMethod -Method POST `
  -Uri https://api.ama-dev.example/api/eval/runs `
  -Headers @{ Authorization = "Bearer $TOKEN" } `
  -ContentType "application/json" `
  -Body $body

$runId = $response.runId
"runId: $runId  estimatedCostAud: $($response.estimatedCostAud)  estimatedDurationMinutes: $($response.estimatedDurationMinutes)"
```

Watch progress (FR-028):

```pwsh
curl -N -H "Authorization: Bearer $TOKEN" `
  "https://api.ama-dev.example/api/eval/runs/$runId/progress"
```

Open the dashboard at `https://ama-dev.example/eval/runs/$runId` to follow live progress. On completion (≤ 8 h, FR-018 / SC-002), the page shows the summary scorecard. The "Sample traces" tab is gated to Tier-2 roles (FR-022).

**Verify**:

- `GET /api/eval/scorecards/$runId` returns three model verdicts with `pass`/`fail` per metric.
- `GET /api/eval/runs/$runId` shows `status: "succeeded"`, `costAttribution.total <= policy.maxRunCostAud`, and `infrastructureLifecycle.terminalState == "clean"` (FR-017, SC-003).
- Reconciler job log (`caj-eval-reconciler-dev`) shows zero orphans for the run window.

## 4. Wire the release gate (one-time)

The gate has two surfaces sharing one scorecard (research D6 / FR-024 / FR-027).

### 4a. GitHub Actions PR check

`.github/workflows/eval-gate.yml` is added to the repo. It:

- Triggers on PRs that change `apps/api/app/prompts/**`, `apps/api/app/services/rag/**`, `infra/bicep/modules/ai/**`, or `packages/eval/**`.
- Calls `POST /api/eval/gate/check` with `mode: "pr-fast-subset"` (≤ 30 min budget, FR-018).
- Posts the resulting scorecard as a check + PR comment.
- Marks the check `failure` if any safety metric falls below threshold or any quality metric regresses beyond `regressionDelta` vs baseline.

**Verify**: open a draft PR that intentionally weakens a refusal-rule and confirm the check fails on first attempt with a sample-level diagnostic (SC-007).

### 4b. Progressive-delivery promotion gate (feature 029)

`infra/policy/promotion-gates/eval-gate.yaml` is referenced from feature 029's promotion pipeline. At `staging → production-canary` promotion, the pipeline calls `POST /api/eval/gate/check` with `mode: "progressive-delivery-full"`. The returned scorecard and signed evidence bundle are attached to the existing 029 evidence pack.

**Verify**: trigger a staged promotion in `dev`; confirm the promotion proposal page shows the eval scorecard alongside the existing 029 SLO and infra-policy gates, and that promotion blocks if the eval gate fails.

## 5. Tear-down (per environment)

Eval platform tear-down is **separate** from per-run tear-down (which is unconditional, FR-017). To remove the eval platform itself in a sandbox subscription:

```pwsh
az group delete -n rg-ama-eval-dev --yes
```

This removes the platform infra; the immutable Blob retention policy means published dataset/run artefacts are still retained for the policy window even after RG deletion only if you used the recommended **separate** storage account in another resource group. For full purge in a sandbox, drop the retention policy first (requires a governance override).

## What "done" looks like

- Three Foundry models score on the same dataset; one scorecard with a clear winner per metric and overall (User Story 1, SC-001).
- Dataset v1.0.0 is immutable, hashed, and approved (User Story 2, FR-009).
- Run resources are provisioned, used, and removed; reconciler reports zero orphans (User Story 3, SC-003).
- A safety-degrading PR is blocked by the gate with a sample-level diagnostic (User Story 4, SC-007).
- Any past run can be reproduced from its evidence bundle by a reviewer who wasn't there (User Story 5, SC-004, SC-012).

## 6. Dev-only anonymous API access (FR-022a)

To make first-time operator validation tractable on a fresh subscription, the **dev environment only** can be
configured to accept anonymous, unauthenticated requests against `/api/eval/*`. Staging and production are
unaffected and continue to enforce the full Tier-1/Tier-2 role model from FR-022 with no anonymous access.

**How to enable**: nothing to do as an operator — the eval Bicep module sets the env vars automatically when
`env == 'dev'`. The API container app receives:

- `ENVIRONMENT=dev`
- `EVAL_ALLOW_ANONYMOUS=1`

The role guard (`apps/api/app/middleware/eval_role_guard.py`) refuses to honour `EVAL_ALLOW_ANONYMOUS` unless
`ENVIRONMENT == "dev"`, so a misconfigured staging/production deployment cannot accidentally turn it on.

**Effective behaviour when on**:

- A request with no `Authorization` header gets a synthetic principal: `sub=anonymous`,
  roles `{Eval.Operator, Eval.Viewer, Eval.Auditor}`, `is_dev_token=True`.
- Audit events tag those calls with `principal=anonymous` **and** `environment=dev`.
- The principal is restricted to the synthetic dev dataset (`disaster-response-core`); access to any other
  dataset returns `403`.
- `GET /api/eval/health` advertises `anonymousAccess: true` so client tooling can detect the mode.
- `scripts/run_llm_evaluation.py` probes the health endpoint; if anonymous mode is on, it omits the
  `Authorization` header entirely for publish/execute/archive (and does not call `az account get-access-token`).
  If the probe fails, it falls back to minting the legacy `dev:<sub>:<roles>` token.

**Verifying staging/production never get the flag**: `infra/bicep/modules/eval/eval-platform.bicep` appends the
`EVAL_ALLOW_ANONYMOUS` env var to the API container app **only inside** an `env == 'dev' ? […] : []` ternary.
The unit test `test_eval_platform_emits_anonymous_env_var_only_in_dev` in
`tests/unit/eval/test_run_llm_evaluation_script.py` enforces this invariant.
