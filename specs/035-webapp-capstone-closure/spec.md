# Feature Specification: Web Application Capstone Closure

**Feature Branch**: `035-webapp-capstone-closure`
**Created**: 2026-05-05
**Status**: Draft
**Input**: User description: "Spec-035 — Web Application Capstone Closure. The previous specification (spec 034) validated the AMA web application against the capstone objectives by authoring a 111-spec Playwright suite, a depth-profile contract, a coverage trace, and a gap register. That validation found that the web application is structurally present (routes load, audit plumbing emits) but lacks the workflow depth required to satisfy the capstone outcomes for many personas, jurisdictions, and cross-sector scenarios. The Playwright suite is now wired correctly; the next gate is the web application itself. The KEY REQUIREMENT for this specification is to close the gaps in the web application at `apps/web/` so that, when the spec-034 web-coverage suite is executed end-to-end, every capstone outcome assertion (SC-001..SC-011) passes against real UI state changes — not against bailing stubs or seed-only echo. Out of scope: changing the validation suite itself, changing the constitution, expanding to Asia-Pacific personas (deferred to spec-028 follow-on)."

## Terminology

The following terms are used interchangeably in this spec, the plan, and the tasks; they are pinned here so subsequent artefacts and the spec-034 web-coverage suite stay aligned.

- **AWS** = Australian Warning System (the three-tier `advice` / `watch-and-act` / `emergency-warning` ladder); never the cloud provider.
- **AWS-level identifier forms**: the canonical machine form is snake_case (`advice` / `watch_and_act` / `emergency_warning`) — used in `data-model.md`, every `contracts/*.md`, every Pydantic / Zod schema, and every task in [`tasks.md`](./tasks.md). The hyphenated form (`watch-and-act` / `emergency-warning`) and the title-cased form (`Watch and Act` / `Emergency Warning`) are display-only (UI labels, prose, headings). Code and selectors MUST use the snake_case form; `data-model.md` § AuditOutcome and the FR-016 cultural-safety contract are authoritative.
- **PIO composer** = AWS warning composer at the public-information-officer workspace (FR-002).
- **Audit row / audit-timeline entry** = a single append-only record on the audit timeline visible to `GET /api/audit/list`. The `outcome` field is the closed-set enum defined in [`data-model.md` § AuditOutcome](./data-model.md).
- **Test-support guard / dual-guard** = the spec-034 dev/test activation gate `AMA_TEST_SUPPORT=1 AND ENVIRONMENT in {dev,test}`; the production-Entra middleware is the contralateral path. Mutual exclusivity is enforced per FR-013 / Clarifications Q8.
- **Q-numbered references** (Q1..Q10) refer to the Clarifications section below.

## Clarifications

### Session 2026-05-05

- Q: Entra ID AppRole granularity for production auth? → A: Option B — 10 AIIMS-function AppRoles + a `persona_id` scoping claim, plus an additional `system-administrator` AppRole with full cross-persona / cross-jurisdiction / cross-route privileges. The 10 AIIMS function roles are `incident-commander`, `operations-officer`, `logistics-officer`, `planning-officer`, `public-information-officer`, `field-coordinator`, `observer-auditor`, `risk-manager`, `resilience-planner`, `executive-leader`. The 11th `system-administrator` role is administrative (not a capstone persona) and is NOT added to the FR-002 inventory of 68; every action it takes is audited with `outcome: admin_override` and the underlying impersonated persona context if any.
- Q: Recovery-handover artefact format? → A: Option A — signed PDF only. The Resilience-Planner recovery-handover composer produces a single digitally signed PDF artefact carrying gap analysis, framework-modelling outputs, lessons integration, and the Sendai counterfactual fields; the audit timeline records `{artefact_hash, signing_identity, export_timestamp}` referenced to that PDF. No JSON sidecar, no per-recipient format selection. Downstream machine ingestion by ICA / state recovery / NEMA is OUT OF SCOPE for spec-035 and deferred.
- Q: Production rate-limit budget shape? → A: Option B — per-`(persona_id, route)` token bucket (default 10 req/min, sustained 600 req/hr) plus a separate global suite-runner ceiling of 600 req/min across the whole CI run. Buckets are keyed on the `persona_id` claim from FR-010; the `system-administrator` AppRole bypasses per-persona buckets but is still bound by the global ceiling. Overages return `429 too_many_requests` with `Retry-After` and an audit row carrying `{persona_id, route, bucket_state, outcome: rate_limited}`. The dev/test dual-guard path MUST NOT be rate-limited. Limits are configurable via App Settings; AVM-deployed primitives (App Service / APIM rate-limit policy) are the implementation surface — no custom infra.
- Q: Offline subsystem architecture? → A: Option B — Service-Worker + IndexedDB queue with a dedicated `/api/offline/replay` endpoint. The PWA service worker intercepts mutating fetches while offline, persists envelopes in IndexedDB keyed by client-generated `correlation_id`, surfaces a degraded-mode banner driven by `navigator.onLine` + heartbeat probe, and on reconnect POSTs queued envelopes to `/api/offline/replay`, which performs server-side dedupe by `(persona_id, correlation_id)` and writes audit rows with `{offline_started_ts, offline_ended_ts, queue_position}`. Browser-native only — no third-party offline SDK, no native-app shell.
- Q: Cultural-safety elder-approval timeout behaviour? → A: Option B — time-boxed approval with life-safety override. Elder/community approval is requested with a configurable timeout (default 90 seconds). On approval the warning publishes and the audit row carries `outcome: approved`. On timeout, behaviour is AWS-level-conditional: (a) AWS `watch-and-act` and `emergency-warning` levels publish in English + Simplified Chinese only with `outcome: cultural_safety_timeout_override`, the ATSI-language variant is suppressed pending approval, an out-of-band notification is dispatched to the elder/community contact, and the override step requires Incident-Commander confirmation; (b) AWS `advice` level publication is BLOCKED with `outcome: cultural_safety_held` and queued as `awaiting-elder-approval`. All three audit outcomes (`approved`, `cultural_safety_timeout_override`, `cultural_safety_held`) carry elder identity (or `none`), AWS level, IC confirmer (if override), and the suppressed/published language variants. The values `cultural_safety_timeout_override` and `cultural_safety_held` are the flat closed-set values defined in [`data-model.md` § AuditOutcome](./data-model.md); the `culturalSafetyState` field on the warning entity continues to use the state-machine enum (`pending_elder | approved | declined | timeout_lifesafety_override | timeout_blocked`).
- Q: Model-gateway classifier deny vs. mask outcome semantics? → A: Option B — deny on PSPF, mask on PII, escalate on conflict, fail-closed on classifier error. (1) PSPF-marked payloads (`OFFICIAL: Sensitive` or higher) are DENIED unconditionally; the operator request returns `403 sovereignty_denied` and the audit row records `outcome: classifier_deny, classifier_layer, content_class: pspf, persona_id, route`. (2) PII-bearing payloads with no PSPF marking are MASKED in place using ADR-033 Layer-2 deterministic redaction rules; the masked payload proceeds to the non-AU model and the operator UI displays a "this content was masked before processing" banner with a link to the unmasked source held in the AU-region store; audit records `outcome: classifier_mask, masked_field_count, persona_id, route`. (3) Payloads with both PSPF and PII are DENIED (PSPF takes precedence) and audited as `outcome: classifier_deny, content_class: pspf+pii`. (4) Classifier failure or timeout is fail-closed (DENY) and audited as `outcome: classifier_failed`.
- Q: Offline-queue cap and replay behaviour beyond SC-007's 50-entry baseline? → A: Option B — hard cap at 500 entries per persona with priority-tiered batched replay. (1) The IndexedDB queue has a per-`persona_id` hard cap of **500 entries** (configurable via App Settings; ceiling enforced server-side at `/api/offline/replay` by rejecting overflow envelopes). (2) **Life-safety-tier entries** (evacuation, AWS warning, GPS hazard report) are admitted unconditionally; if the cap is reached, life-safety entries displace the oldest **routine-tier** entries (the displaced entries are persisted to a side-buffer and audited `outcome: queue_displaced, displacing_correlation_id`). (3) The operator UI MUST surface a queue-depth indicator showing `X / 500` and a sub-counter `Y life-safety reserved`, with a warning state at ≥80% of cap. (4) On reconnect, replay is **batched and tiered**: life-safety tier first (≤30 s for ≤50 entries per SC-007 baseline), then routine entries in batches of 50 with a target of **≤30 s per 50-entry batch** and a global ceiling of **≤5 minutes for a full 500-entry drain**. (5) Any envelope rejected on overflow at `/api/offline/replay` MUST append an audit row `outcome: queue_overflow, persona_id, correlation_id, queue_depth_observed` on reconnect.
- Q: Activation-mutex enforcement point between production-Entra and dev/test dual-guard? → A: Option D (modified) — **both build-time CI gate AND container-startup lifespan invariant, with the CI gate exempt for the `dev` environment**. (1) **Build-time CI gate**: `apps/api/` MUST carry a static check (run in CI for any `ENVIRONMENT in {test, staging, production}` build) verifying that `outcome_evaluator.py` and `audit_list.py` carry the dual-guard check AND the production-Entra middleware is wired into the FastAPI app factory; CI MUST fail the gate if either is missing OR if a build resolves both `ENVIRONMENT=production` and `AMA_TEST_SUPPORT=1`. The gate MUST NOT run for `ENVIRONMENT=dev` (developer-loop builds are exempt to preserve fast iteration; the runtime invariant remains the safety net for `dev`). (2) **Container-startup lifespan invariant** (all environments including `dev`): on FastAPI boot, a `lifespan` hook MUST read the resolved environment plus AppSettings and refuse to start the app (process exits non-zero) if both activation paths resolve true; a startup-failure audit row MUST be appended to the audit timeline with `outcome: activation_mutex_violation, environment, ama_test_support, app_role_middleware_loaded` before exit. (3) The audit row MUST be observable on the next successful boot (audit store reachable independent of app boot path) so co-activation failures are post-mortem-discoverable.
- Q: `system-administrator` impersonation surface and audit shape? → A: Option A — explicit `X-Impersonate-Persona` header per request with paired audit rows. (1) Impersonation MUST be invoked via an explicit `X-Impersonate-Persona: {persona_id}` HTTP header on each request; **sticky session impersonation is forbidden** (the admin cannot "switch into" a persona for a session). (2) Each impersonated request inherits the AIIMS-function authorisation of the target persona for the route family but executes under the admin's bearer identity. (3) Each impersonated request MUST emit **two audit rows in a single transaction** within the ≤2 s SLO: row 1 `outcome: admin_override, operator_identity: <admin>, impersonated_persona_id: <target>, route, sc_id|null, correlation_id`; row 2 carries the action's normal outcome with `operator_identity: <admin>, persona_id: <target>, impersonated_by: <admin>, route, correlation_id`. (4) `GET /api/audit/list` MUST NOT hide either row from any caller authorised to read the timeline. (5) Impersonation requests against the model gateway remain subject to FR-027 — PSPF/PII deny/mask outcomes are NEVER bypassed by the admin role. (6) Direct admin actions (no `X-Impersonate-Persona` header) emit a single `outcome: admin_override, impersonated_persona_id: none` row.
- Q: How are spec-035 production-only errors (401, 403 forbidden, 403 sovereignty_denied, 429) reconciled with the spec-034 evaluator error contract? → A: Option B — explicit additive contract extension layered on spec-034 with deterministic precedence. (1) Spec-035 introduces a contract layer named **"spec-034 contract + production-auth extension"**. The spec-034 success-body shape `{status, evidence_refs[], metric_value, threshold, audit_id}` is preserved verbatim; spec-035-only errors share a uniform extension envelope `{error_code, retry_after_seconds | null, audit_id, correlation_id}` with HTTP status mapping `error_code: unauthorized → 401`, `forbidden → 403`, `sovereignty_denied → 403`, `rate_limited → 429`. (2) The spec-034 web-coverage suite (running in production-reachable mode per FR-030) MUST treat the new error codes as **expected outcomes** keyed off the persona's bearer-token state — 401 / 403 / 429 are asserted positively in the auth-rbac, rate-limit, and sovereignty cross-cutting specs and MUST NOT bail the suite. (3) **Spec-034 OOS-006 (error contract is locked) is preserved** — spec-035 does NOT modify the SC-001..SC-005 evaluator response shape or the existing spec-034 error codes (`400 evaluator_not_routable`, `404 scenario_not_found`, `422` schema, `503 seed_not_ready`); it only adds new error rows and the extension envelope. (4) **Precedence (highest to lowest)** when multiple errors apply to a single request: (i) `400 evaluator_not_routable` for sc-006..sc-011 (spec-034 routability is checked first regardless of auth); (ii) `403 sovereignty_denied` (FR-027 PSPF — NN-1 sovereignty wins over auth); (iii) `401 unauthorized` (FR-010 missing/invalid bearer); (iv) `403 forbidden` (FR-011 stage-b persona↔role mismatch); (v) `429 too_many_requests` (FR-012 bucket exhaustion); (vi) `422` schema and `503 seed_not_ready` (spec-034). (5) `400 evaluator_not_routable` for sc-006..sc-011 MUST return regardless of bearer-token state to preserve the spec-034 invariant.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Safety-critical operator workflows drive real state changes (Priority: P1)

A capstone evaluator opens the deployed web application at `https://app-ama-zo6bb5.azurewebsites.net/` and runs the spec-034 web-coverage suite end-to-end. The 10 operational persona scenarios — Incident Commander, Planning Officer, Public-Information Officer, Logistics Officer, Operations Officer, Field Coordinator, Observer-Auditor, Risk Manager, Resilience Planner, Executive Leader — each drive a state-changing workflow against the real UI: cross-agency-action approval, AWS warning composition + IC approval + publish (with at least one community-language variant), offline GPS hazard capture and reconnect-replay, audit-tamper-attempt-and-read-back, live risk-matrix recommendation, and response-to-recovery handover artefact. Every scenario asserts the persisted post-transition state via either an FR-028 evaluator endpoint or a stable UI selector AND reads back the audit-timeline entry within the 2-second SLO.

**Why this priority**: Without operator workflow-state surfaces, SC-001 (≤2 minute warning reach), SC-002 (≤5/15/30 minute decision-to-action latency), and the FR-009 / FR-010 / FR-011 / FR-014 cross-cutting assertions cannot pass against production. This is the smallest meaningful slice that delivers capstone-outcome value: ten passing operational personas + one cross-cutting AWS multilingual composer = SC-001 + SC-002 + the AWS-compliance, audit-append, span-of-control, and accessibility cross-cutting specs all green. Every other priority depends on this slice landing first because the PIO composer and IC approval card are reused by the sector-level personas in P3.

**Independent Test**: Run only the `tests/e2e/web-coverage/operational/` shard and the cross-cutting specs `aws-warning-compliance.spec.ts`, `audit-append-only.spec.ts`, `span-of-control.spec.ts`, `accessibility-and-multilingual.spec.ts`, `field-offline-mode.spec.ts` against the production endpoint. Suite passes with ≥95% of (persona × outcome × hazard) tuples in `pass` state and zero `Open` HIGH+ entries in `gap-register.json` for the operational personas.

**Acceptance Scenarios**:

1. **Given** an Incident Commander signed in with the AIIMS `incident-commander` AppRole and an active cross-agency action awaiting decision, **When** the IC opens the action card, supplies a rationale, source reference, confidence pill (low/medium/high), records the approver identity, and presses Approve, **Then** the action transitions to `approved` in the UI within one COP refresh, the audit timeline records `{operator_identity, rationale, source_refs, confidence, audit_id, correlation_id}` within ≤2 seconds, and a re-fetch of the action returns the new state with no need for page reload.
2. **Given** a Public-Information Officer composing an Emergency Warning for a tropical-cyclone scenario in QLD, **When** the PIO selects the AWS level (Advice → Watch and Act → Emergency Warning), enters hazard / location / action statement, picks at least one community-language variant (Simplified Chinese plus an ATSI-language placeholder for the affected community), passes the in-page accessibility scan (alt text, semantic landmarks, contrast, screen-reader announcements), submits the draft for IC approval, and after approval presses Publish, **Then** the warning is persisted with a published payload, no publish path exists that bypasses IC approval, the audit row records language-variant evidence and approver identity, and SC-001 (≤2-minute reach including community-language render) holds in the trace artefact.
3. **Given** a Field Coordinator working offline in a degraded-comms area, **When** the operator captures a GPS-tagged hazard report, places three further reports into the local queue, and reconnects after up to 30 minutes, **Then** the queued reports replay in original authoring order with original timestamps preserved, idempotent dedupe by client correlation ID prevents double-count, the audit timeline records each report with offline-window metadata (`offline_started_ts`, `offline_ended_ts`), and a degraded-mode banner is dismissed only after the queue empties.
4. **Given** an Observer-Auditor who attempts to PATCH or DELETE an audit-timeline row via the UI, **When** the mutation is submitted, **Then** the request is rejected with a UI surface that declares the timeline append-only (no silent failure), an audit-timeline entry is appended recording `outcome: denied`, the operator persona, and a non-empty rationale, and a subsequent read-back of the original row demonstrates byte-identical content. An export-to-evidence action produces a downloadable artefact whose hash is recorded in the audit trail.
5. **Given** an Incident Commander already supervising 7 direct reports in an active incident, **When** the IC adds an 8th, **Then** the UI surfaces a span-of-control warning before save with delegation options, and the warning text references AIIMS guidance; the negative test for the same scenario on a Planning Officer (read-only span-of-control role) shows the warning is correctly suppressed.

### User Story 2 — Capstone evaluator and audit-list endpoints reachable in production with auth and RBAC (Priority: P2)

The spec-034 web-coverage suite runs end-to-end against the production endpoint, calling `POST /api/outcomes/sc-{001..005}/evaluate` and `GET /api/audit/list?correlation_id={uuid}&cycle={current|all}` with an Entra ID-issued bearer token bound to an AIIMS persona AppRole. The endpoints honour the spec-034 contract (idempotency tuple, response shape, ≤2-s audit-append SLO, cursor pagination, append-only retention, error contract) and add (a) Entra ID authentication, (b) AIIMS-function-based authorisation (incident-commander / operations / logistics / planning / public-information / field-coordinator / observer-auditor / risk-manager / resilience-planner / executive-leader plus the 58 sector personas via existing AppRole mapping), (c) per-route audit of every call (whether allowed, denied, or rate-limited), and (d) bounded rate-limit per persona. The dev/test dual-guard remains intact for the suite's CI shard, but production reachability is the new contractual surface (per `00-overall-brief.md` § Acceptance bar bullet 4 and Pass-5 Q25/Q29 supersede).

**Why this priority**: Without this slice the suite cannot run against production at all — every workflow-state assertion in P1 is observable only via the evaluator endpoint and the audit-list read-back, both of which are currently dual-guarded off in `production` (verified at `apps/api/app/api/routes/outcome_evaluator.py:11-14` and `audit_list.py:9-13`). P2 is below P1 because P1 builds the operator-facing affordances; P2 unlocks the capstone evidence stream that proves P1 holds in production. Without P2, P1 still works in dev/test (where the suite can run today) so the slices remain independently testable.

**Independent Test**: Acquire an Entra ID bearer for a fixture persona (any AIIMS AppRole). Call `POST /api/outcomes/sc-001/evaluate` and `GET /api/audit/list` against `https://app-ama-zo6bb5.azurewebsites.net/`. Both return 200 with bodies matching the spec-034 contract, the call appears in the audit timeline, and an unauthorised caller (no token, expired token, or wrong AppRole) is rejected with an `auth_*` error and a denial audit row.

**Acceptance Scenarios**:

1. **Given** an Entra ID bearer token for an `incident-commander` AIIMS AppRole and a valid `EvaluatorRequest` body for `sc-001` with a known `scenario_id`, **When** the suite POSTs to `/api/outcomes/sc-001/evaluate` against the production endpoint, **Then** the response matches the spec-034 contract (`{status, evidence_refs, metric_value, threshold, audit_id}`), the audit-append latency is ≤2 s, and a follow-up `GET /api/audit/list?correlation_id={uuid}` returns the evidence row.
2. **Given** the same request with the same idempotency tuple `(sc_id, scenario_id, persona_id, correlation_id)`, **When** the call is repeated within the cycle window, **Then** the same `audit_id` and verdict are returned with no fresh audit row.
3. **Given** an unauthenticated call (missing or expired token), **When** the suite POSTs to `/api/outcomes/sc-001/evaluate`, **Then** the response is `401 unauthorized` and the call is recorded in the audit timeline as `outcome: auth_unauthorized`; for a valid token without the required AppRole the response is `403 forbidden` and the audit row carries `outcome: auth_forbidden`. No evaluator computation is performed in either case.
4. **Given** an authenticated caller exceeding the per-persona rate limit, **When** the next call is made, **Then** the response is `429 too_many_requests` with a `Retry-After` header and the rate-limit hit is recorded in the audit timeline.
5. **Given** an out-of-range `sc_id` (e.g., `sc-006..sc-011`), **When** the suite POSTs, **Then** the response is `400 evaluator_not_routable` with the CI-job owner named in the body — preserving the Pass-5 Q29 contract that SC-006..SC-011 are CI-artefact-derived.
6. **Given** the same suite running in CI under `AMA_TEST_SUPPORT=1` and `ENVIRONMENT in {dev,test}`, **When** the suite calls the evaluator without a production bearer, **Then** the dev/test dual-guard path activates (no Entra dependency), the spec-034 contract is satisfied, and the production-reachable code path remains inert in that environment.

### Edge Cases

- **Persona without a tailored workspace** beyond the generic `PersonaWorkspace` shell: scenario fails fast with `GAP-WORKSPACE-MISSING`; the row is added to the spec-034 gap register; spec-035 implementation must add the persona's safety-critical-workflow card without inventing a new persona ID.
- **Production caller lacks Entra AppRole** mapped to an AIIMS function: caller is rejected with `403`, audit row records `outcome: auth_forbidden` with attempted persona ID; suite's production shard treats this as a configuration defect, not a UI gap.
- **Dual-guarded dev/test path active in production accidentally**: spec-035 implementation MUST emit a build-time check that fails CI when `AMA_TEST_SUPPORT=1` is set with `ENVIRONMENT=production`. The two activation paths are mutually exclusive; never co-active.
- **Idempotency-tuple collision across cycles**: a fresh `correlation_id` triggers a fresh evaluation per Pass-4 Q21; the audit-list read-back returns the new row alongside the old one when `cycle=all` is passed.
- **Span-of-control breach on a sector persona** (e.g., SES-NSW field supervisor with 8 reports): warning fires only for the Tier-1 / Tier-2 command-side personas enumerated in spec-034 FR-020; a sector persona NOT in the command chain has the warning suppressed (negative test asserts).
- **Cultural-safety template invoked without a community-elder identity available**: per FR-016 (Clarifications Q5), behaviour depends on AWS level — `advice` level blocks publication, queues as `awaiting-elder-approval`, and audits `outcome: cultural_safety_held`; `watch-and-act` / `emergency-warning` levels apply the time-boxed override path (English + Simplified Chinese only, ATSI variant suppressed, IC confirmation required, audited as `outcome: cultural_safety_timeout_override`).
- **Multilingual variant unavailable for the selected hazard**: the fallback chain renders the highest-priority available variant + English, surfaces a `language_pack_missing` UI badge, and audits the fallback choice — no silent omission.
- **Offline queue overflow** beyond device-storage cap: oldest entries persist, newest are rejected with a clear UI banner, the rejection event is queued for audit on reconnect, and life-safety-critical actions (evacuation, warning) take precedence over routine entries.
- **Recovery handover artefact exceeds signing-key TTL**: artefact generation is blocked with a clear UI message; the operator is redirected to the key-rotation procedure; no unsigned artefact is ever emitted.
- **Sovereignty banner suppressed by ad-blocker or extension**: the banner is implemented as a non-suppressible part of the page chrome (not a third-party widget) and verified by the cross-cutting accessibility scan that the banner exists in the rendered DOM.
- **Foundry carve-out registry stale (`review_date` > 90 days)**: the UI renders a `carveout_review_overdue` warning on every affected route and the suite emits `GAP-CARVEOUT-STALE` per spec-034 FR-018(c).
- **Concurrent IC approval attempts** on the same action: the second approver sees a stale-state `409 conflict` UX, the conflict is audited, and the action's final state reflects the first-write-wins decision.
- **Audit-list `cycle=all` exceeds pagination cap**: the response surfaces `next_cursor` and the UI surfaces a "load more" affordance; the cursor remains stable across the read window.
- **PSPF-marked content in a translation pipeline**: the gateway denies the translation request before the payload reaches a non-AU model; the denial appears in audit; the operator is offered a manual-translation fallback.
- **Mining-corridor cascade** (WA iron-ore + cyclone): the infrastructure-overlay surface shows port / rail / power-corridor priorities, mutual-aid sequencing UI shows the DFES + WA Police + private-sector triage; if any operator persona is unauthorised for the private-sector view the UI shows a placeholder with audit of the redaction.

(b) **PII-bearing content with no PSPF marking** MUST be MASKED in place using ADR-033 Layer-2 deterministic redaction rules; the masked payload proceeds to the non-AU model; the operator UI MUST display a "this content was masked before processing" banner with a link to the unmasked source held in the AU-region store; the audit row records `outcome: classifier_mask, masked_field_count, persona_id, route`. (c) **Payloads with both PSPF and PII** MUST be DENIED (PSPF takes precedence) and audited as `outcome: classifier_deny, content_class: pspf+pii`. (d) **Classifier failure or timeout** MUST fail-closed (DENY) and audit `outcome: classifier_failed`. Every outcome MUST be observable via `/api/audit/list` with the classifier-layer identity.
- **FR-028**: System MUST satisfy WCAG 2.2 AA on every P1 operator surface enumerated in spec-034 FR-014 (persona workspaces, governance dashboard routes, AWS composer, simulation control surfaces, audit-timeline view); a failing surface MUST emit `GAP-A11Y-WORKSPACE` and block the gate.
- **FR-029**: System MUST honour the multilingual baseline (Simplified Chinese v1 + ATSI-language placeholder) on every public-warning surface, plus jurisdiction-specific language packs (palawa for TAS, Yolŋu Matha / Pitjantjatjara / Warlpiri for NT, Kimberley/Pilbara dialects for WA), with a visible fallback chain (en → community-language → en) and no silent translation drop.
