# Data Model: LLM Deployment Routing and Provenance

> Generated by SpecKit planning agent | 2026-10-18

## 1. OperationalTier

Closed chat enum: `reasoning`, `drafting`, `simulation`. Tier expresses purpose,
not model size, model family or resource name. `embedding` remains an existing
lookup consumer, not a fourth chat tier. Unknown chat tiers fail before dispatch.

## 2. ModelIdentity

| Field | Type | Validation / meaning |
| --- | --- | --- |
| model_id | non-empty string | Underlying configured model identifier, not a deployment alias |
| model_version | non-empty string | Opaque provider version, never parsed from a name |
| model_key | derived string | `model_id@model_version`; compatibility coordinate, not tier identity |

Many DeploymentIdentity records may share one ModelIdentity. API version is a
transport property, not model_version. No model is selected by this design.

## 3. DeploymentIdentity

| Field | Type | Validation / meaning |
| --- | --- | --- |
| account_resource_id | string | Environment-specific approved parent |
| deployment_name | non-empty string | Child name as configured; preserve explicit existing names |
| model | ModelIdentity | Independent from deployment_name |
| region | string | Approved existing endpoint placement |
| sku | string | Approved existing value, no default substitution |
| capacity | positive integer | Preserve existing allocation and unit semantics |
| rai_policy_name / policy evidence | string / baseline reference | Preserve attachment and effective filters |
| access_controls | baseline evidence reference | Preserve managed identities, roles, network and local-auth posture |
| version_upgrade_option | string or unavailable | Capture observed/effective setting; no AVM-default drift |

Identity key is `(account_resource_id, deployment_name)`. Simulation's
deployment must be distinct from reasoning/drafting in the same account;
otherwise fail the isolation validation. Multiple deployments sharing a model
is allowed; it does not collapse their resource identities. Other shared-tier
topologies require their approved baseline and must not be silently rewritten.
Compare simulation to effective live-tier destinations resolved from the same
account snapshot, including alias/exact/base legacy paths without explicit
live-tier env. An unresolved required comparison fails closed for simulation.

## 4. TierConfiguration (immutable, in process)

| Field | Type | Source |
| --- | --- | --- |
| tier | OperationalTier | Caller purpose |
| deployment_name | string or absent | `AZURE_AI_<TIER>_DEPLOYMENT` |
| model_id / model_version | strings or unavailable in legacy configuration | New `_MODEL_ID` / `_MODEL_VERSION` |
| legacy_model_key | string or absent | Existing `_MODEL_KEY` compatibility setting |
| metadata_source | enum | `configured`, `legacy_coordinate`, `unavailable` |
| configuration_revision | process/release reference | Image/config snapshot identity |

New infrastructure-generated configuration contains all fields and consistent
derived model keys. An absent explicit setting is different from an explicitly
empty one: reasoning/drafting may use an absent-setting legacy path; an empty
explicit value is invalid. Simulation requires the explicit deployment even if
there is a model key. Partially supplied new metadata is invalid; fully absent
legacy identity may remain unavailable for auditing. A complete configured
model identity must agree with a supplied compatibility coordinate.
Legacy identity is admitted only with a proven association to the resolved
deployment/account: a validated same-destination coordinate mapping or a
target/config-bound verification reference. Unique coordinate-to-B metadata
cannot describe explicit A. With new fields absent and association unproven,
retain A and unavailable metadata rather than rerouting or borrowing identity.

## 5. RoutingConfiguration / LegacyRoutingEntry

RoutingConfiguration contains endpoint, region, tier configurations, the raw
compatibility CSV, and validated `routing_key -> deployment_name` entries.
Capture source presence as well as values; do not mix frozen config with
subsequent environment reads.

LegacyRoutingEntry fields: `routing_key`, `deployment_name`, source position
for diagnostic purposes only. Keys and values are trimmed and non-empty.
The CSV grammar and precedence are in
[contracts/routing-configuration.md](contracts/routing-configuration.md).

Invariants:
- Validate raw entries before constructing a dictionary.
- Equal key/equal destination repeats are idempotent.
- Equal key/different destinations is invalid in every ordering.
- Metadata coordinates may repeat across tiers; CSV routing keys may not
  designate different destinations.
- Explicit tier precedence does not make an internally conflicting map valid.
- Embedding keys/destinations remain independent and are preserved.

## 6. ResolvedDeployment (ephemeral)

| Field | Type | Meaning |
| --- | --- | --- |
| tier | OperationalTier or absent | Absent for a direct legacy model-key caller |
| deployment_name | non-empty string | Actual destination to pass to SDK |
| model_id / model_version | string or unavailable | Configured/verified metadata, not guessed |
| resolution_source | enum | `explicit_tier`, `tier_alias`, `legacy_exact`, `legacy_base` |
| configuration_revision | reference | Snapshot used for resolution |
| verification_reference | optional reference | Release preflight, not live-response execution proof |
| metadata_association_reference | optional snapshot/evidence reference | Links admitted legacy identity to this destination/account, not merely a unique key |

One result is reused for routing, telemetry and audit; do not resolve again at
audit time. An error returns no result and does not send inference.

## 7. InferenceAttemptEvidence and audit projections

Per SDK request, including each controller tool-loop round:

| Field | Type | Meaning |
| --- | --- | --- |
| call_id / correlation_id | string | Attempt identity and existing turn/run correlation |
| resolved_identity | ResolvedDeployment or absent | Available target, not proof of invocation |
| inference_attempted | boolean or null | True with request-submission evidence; false only if known not submitted; null if dispatch/remote/legacy evidence unavailable |
| inference_outcome | `succeeded`, `failed`, `not_attempted`, `unknown` or null | Never derive success from configuration or HTTP invocation |
| error_code | optional existing error code | Preserve configuration/transport/gateway distinctions |
| output provenance | existing usage/hash fields | Actual model response usage, not template text attributed to the model |

State transitions:

```text
unresolved -> validated -> ready -> request_attempted -> succeeded | failed
     \            \          \
      -> not_attempted <-------+    (pre-call config / credential / gateway failure)

remote invocation with response lost -> unknown (until correlated evidence exists)
request_attempted -> unknown completion (submission proved, no terminal evidence)
```

Credential/client construction or entry to an SDK method alone is not
request_attempted. Local SDK validation failures and gateway-denied requests
stay not_attempted. Timeout after submission is attempted/failed; if submission
cannot be established, attempt status is unknown. Neither claims that the
provider completed execution. Safety/template fallback
after a real completion retains true attempt evidence and original usage.
Use the request-bound outbound transport handoff signal defined in
[the provenance contract](contracts/inference-provenance.md#evidence-boundary-and-per-surface-admission);
SDK/agent method entry and HTTP correlation alone are insufficient.

Projection rules:
- Existing strict `AuditRecord` / `audit-record-llm-call.json` retains required
  string `model_id`, `model_version`, `deployment_alias`. Use repository
  `unknown` convention when an actual attempt's metadata is unavailable.
- Add optional nullable `inference_attempted` / `inference_outcome` to readers,
  schemas and writers together. Historical absence means unavailable, not
  inferred success. Keep `call_kind` as inference/embedding; do not invent a
  no-inference LLM-call row.
- Admission for new inference/usage call rows requires true submission
  evidence: one eligible row per distinct proved call ID at the owning writer,
  whether completion succeeded, failed or is unknown. False or unknown
  submission admits zero inference rows; retain uncertainty in existing
  agent/simulation/invocation envelopes, never discard the remote outcome.
  Follow the contract's per-surface matrix and writer-level row counts;
  preserve existing opt-out/ownership/deduplication rules.
- Dispatcher / SubAgentReply retains nullable `model_deployment` and adds
  optional `model_id`, `model_version`, attempt/outcome and error provenance.
- Existing SubAgentInvocationRecord's required string `model_deployment` uses
  `unknown` when unavailable; optional identity/attempt fields are additive.
  The HTTP agent invocation record remains valid without asserting inference.
- Preserve RAG, prompt hash, citations, tenant partition, correlation,
  AIIMS/outcome and append-only invariants. No historical updates or migrations
  that rewrite records.
  Historical uncertain records remain readable; new-write admission is not a
  retrospective validity constraint.

## 8. ApprovedEnvironmentBaseline (release evidence)

One reviewed baseline per target environment, containing environment,
subscription/account/scope, collection timestamp, approver/reference, three
DeploymentIdentity entries, embedding identity/protections and current
image/configuration revisions. Include repository proposal versus verified
Azure properties and a reconciliation decision for each difference.
Include scoped G0 collection-authority reference, approved freshness/
invalidation policy and version, target identifiers, timestamps, evidence
source revisions, candidate config digest, API/agents image revisions and
compiled IaC/parameter revision binding or explicit reconciliation.

States: `uncollected -> observed -> reconciled -> approved`. Missing access,
unverified metadata or disagreement prevents approved state. Observed dev
properties alone cannot populate other environments. Baseline is evidence,
not a newly provisioned database.
Approval is not indefinite validity: policy window expiry, drift, affected
scope/config/image/proposal/protection/policy changes or missing bindings
invalidate dependent evidence and require authorised refresh/reapproval.
Missing/unapproved policy fails target readiness closed; no universal TTL.

## 9. NamingMigrationRecord (separately approved procedure/evidence)

Fields: environment, approval reference, old/new deployment identity sets,
unchanged model/protection comparisons, effective governance reference, quota
pool/headroom evidence, readiness results, old/new paired image/configuration
revisions, switch results, rollback results, retention decision and separate
retirement approval.
Bind migration evidence to the same target/revisions and approved freshness/
invalidation policy. Distinguish synthetic procedure verification from real
G5 operational evidence; only actual authorised forward/rollback checks can
satisfy SC-006 migration acceptance. G6 remains separate.

States:

```text
proposed -> approved -> replacements_ready -> switched -> verified -> retained
                                      \         \-> rolled_back
retained -> retirement_approved -> retired
```

No transition automatically provisions, switches or deletes anything.
Initial rollout does not enter this resource-migration state machine.
