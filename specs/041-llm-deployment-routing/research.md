# Research: LLM Deployment Configuration and Routing

> Generated by SpecKit planning agent | 2026-10-18

## Scope and method

Repository exploration resolves the design questions without independent
research agents. No live Azure inventory, inference, deployment, deletion,
configuration mutation, model discovery/selection or SDK upgrade was performed.
The supplied live dev observations remain contextual, not independently
verified approved baselines. No clarification Q&A is needed or fabricated.

Evidence includes `infra/modules/azure-openai.bicep`, `infra/main.bicep`,
the three environment `.bicepparam` paths, common/MAF/dispatcher/controller
clients, eval/ingest/query embedding consumers, audit writers and strict
schemas, existing contract tests and governance instructions/artifacts.
Azure MCP AI application best-practice guidance was consulted read-only;
generic SDK/model recommendations do not authorise changing this repository's
models, framework, endpoints or evaluation strategy.

## R1 — Independent identity and immutable configuration

**Decision**: Represent tier, deployment name, model identifier and version as
distinct fields. Snapshot per-tier env settings at construction, alongside
endpoint/region/legacy CSV; refresh only by a new process/revision. Derive
`MODEL_KEY` compatibility coordinates from model metadata, never deployment names.

**Rationale**: `LLMClientConfig` is frozen but `foundry_model_key_for` reads tier
env dynamically. Identical model/version coordinates are valid for different
deployment resources; a dictionary keyed only by model cannot preserve purpose.

**Alternatives considered**: Rename deployments to infer identity (unsafe and
still wrong); require different models for each tier (unauthorised model change);
live ARM queries on every request (latency, availability and permissions coupling).

## R2 — One chat resolver, transport-specific adapters

**Decision**: Put shared pure chat resolution with existing common configuration.
Return resolved deployment plus metadata/provenance to all transport adapters.
Retain factory signatures, test injection, AAD scope, gateway, endpoint shaping,
cache semantics and controller's direct streaming SDK.

**Rationale**: MAF consumes a tier alias from `foundry_model_key_for` but only
checks CSV or test-only deployment fields. Dispatcher picks simulation model
key first and can fall back to reasoning. Common `_resolve` checks the map
before explicit tier env. Controller explicit precedence is correct when set,
but its missing-explicit fallback also violates isolation. Sharing resolution
fixes these defects without a transport rewrite.

**Alternatives considered**: Patch four precedence chains separately (drift);
replace every SDK with one new client (unrelated churn); let simulation fall
back to a shared key (cannot prove isolation).

## R3 — Strict validation, explicit precedence, staged compatibility

**Decision**: Validate raw CSV before converting to a dictionary. Duplicate
identical pairs are idempotent; the same key with different destinations is an
error naming the key and destinations. Missing values and malformed entries are
errors rather than silently skipped. A valid explicit tier overrides a valid
map alias/model mapping, but does not excuse an internally conflicting map.
Simulation requires non-empty explicit `AZURE_AI_SIMULATION_DEPLOYMENT`.

**Rationale**: Both common parsers use `setdefault`; eval/ingest use independent
parsers and may have different winner semantics. Current tests pin first-write
wins, so merely preserving green tests would preserve the defect. Validation
must happen before information is lost, and before the affected inference.

**Alternatives considered**: First/last wins (order dependent); reject shared
model identity (legitimate configuration); ignore all map errors when tier env
exists (contradicts ambiguous-map acceptance); strict reader first in production
(would reject today's deployed CSV).

**Rollout resolution**: Prepare cleaned producer output and candidate environment
first; pair them with the strict application image in inactive revisions and
validate before activation. Never put the strict reader into an active old
ambiguous snapshot. No permanent compatibility bypass or ambiguous legacy
selection is introduced.

**Isolation refinement (U2)**: Compare simulation with effective reasoning/
drafting destinations under the same account snapshot after explicit/alias/
exact/base resolution, even with no live-tier explicit env settings. Test
mixed explicit/legacy live paths and all three legacy paths against simulation;
unresolved required comparisons cannot be treated as isolation proof.

## R4 — CSV evolution without losing embedding or model-key users

**Decision**: Keep `AZURE_AI_PROJECT_DEPLOYMENTS` CSV. Emit stable tier aliases
for chat and retain model-key entries only when each key has one unique
destination. Omit shared ambiguous model coordinates rather than pick a tier.
Always retain the unchanged embedding model/version entry; preserve direct
`EMBEDDING_DEPLOYMENT_NAME` query consumers. Maintain exact, then unambiguous
base-key compatibility for non-simulation legacy callers.

**Rationale**: Tier aliases are already recognised by common chat and usable
as old MAF map keys. JSON-only replacement would break ingest/eval/health
consumers. Eval runs need a deliberately selected unambiguous per-run map
when one model has several tier deployments; this does not change evaluation
strategy. Parsers in separate apps use conformance tests, not cross-app imports.

**Alternatives considered**: Repeat the shared key three times (root defect);
drop embedding entries (regression); add a new distributed routing service
or config dependency (unnecessary); silently map shared model to reasoning
(violates FR-009/010 and simulation isolation).

## R5 — Top-level infrastructure contract and preservation

**Decision**: Expose deployment name, model name and model version for each chat
tier at `infra/main.bicep`; explicitly pass all nine fields to the child.
Names for new resources default to `reasoning-${environmentName}`,
`drafting-${environmentName}`, `simulation-${environmentName}` within the
account namespace. Existing environments must supply approved existing names.
Model and version require approved environment values, not universal defaults.
Return independent per-tier metadata and compatibility model keys.

**Rationale**: Current child defaults all models to `gpt-5.6@2026-03-05` and
hardcodes model-shaped deployment names; main passes none of those model
selections. Supplied dev `gpt-5.4` observations cannot authorise any upgrade,
downgrade or selection for other targets. Existing single-SKU/capacity/policy
defaults are not evidence of a target's approved operating baseline.

**Alternatives considered**: Rename existing resources immediately (P2 migration);
choose a mini model to match a label (explicitly excluded); blindly retain
repository defaults (can provision different models); change global SKU or
RAI policy while fixing naming (scope violation).

## R6 — Identity metadata and verification

**Decision**: Publish `AZURE_AI_<TIER>_MODEL_ID` and `_MODEL_VERSION` separately
from `_DEPLOYMENT`; retain derived `_MODEL_KEY` for compatibility. Verify the
environment's configured model/version against Azure deployment properties
before activation/provisioning. Store verification evidence with the release,
not secrets or full prompts. Configured identity is not response-observed
execution evidence.

**Rationale**: Controller currently writes `model_id=deployment` and a global
version/`unknown`. Names such as `gpt-5.4-mini-dev` do not identify hosted models.
Legacy metadata may be unavailable; string audit fields already use `unknown`
and optional reply fields already use null. Preserve those conventions instead
of inferring identity from names.

**Association refinement (U1)**: Resolve destination before admitting legacy
identity. A unique exact coordinate is not proof it describes that destination:
require its validated map entry to select the same deployment/account, or
target/config-bound verification of that association. Explicit A with absent
new identity and coordinate-to-B retains A with unavailable metadata. Matching
A may supply legacy identity; base-only keys never invent version. This
preserves explicit precedence without attributing B's model to A.

**Alternatives considered**: Split deployment names (false provenance); global
model/version values (wrong when tiers differ); fabricate response-reported
model from configured values (not truthful).

## R7 — Audit attempt boundary and historical compatibility

**Decision**: Carry nullable `inference_attempted` and `inference_outcome`
evidence plus independent identity through response/usage/audit adapters.
Mark true only at the request-submission boundary after configuration, credential,
gateway and local SDK validation; true means attempted, not remotely executed
successfully. Entering an SDK method alone is not proof of submission: known
local validation failures remain not_attempted, and uncertain dispatch is unknown.
Use existing error/agent-event records for pre-request degradation. Emit an
inference record only for a proved submitted request. Extend strict reader/schema
support additively before producers emit new optional fields.

**Rationale**: Dispatcher HTTP invocation IDs are not inference proof. The API
adapter fills HTTP failures with obsolete role labels. Controller's RAG-success
audit block misses no-RAG and failed-request coverage; each tool-loop request
must retain its own evidence even if a later round fails. MAF agent middleware
also wraps tools/policies, not exclusively model calls.

**Alternatives considered**: Treat any degraded response as no call (wrong
after transport failure or safety fallback); treat every agent invocation as
inference (fabricates calls); backfill or rewrite old rows (forbidden);
make all old identity fields nullable (unnecessary schema break).

Use `unknown` for unavailable required string identity fields, null for
existing nullable provenance fields, and unknown/null attempt evidence for
legacy or unobserved remote outcomes. Never infer zero remote attempts from a
timeout. Keep existing prompt/RAG/citation/AIIMS invariants.

**Admission refinement (I2)**: The provenance contract's per-surface matrix is
normative for all new writers. A request-bound outbound SDK transport handoff
signal with call ID/resolved destination proves submission; method entry or
HTTP invocation does not. True submission admits one eligible inference row
per distinct call ID at its owning writer (including true/unknown completion);
false/not_attempted and null/unknown submission admit zero. Preserve unknown
remote outcomes in existing event/invocation envelopes; do not fabricate a row
to retain uncertainty. Distinguish a locally observed submitted timeout
(true/failed) from proved remote submission without terminal evidence
(true/unknown), and from unknown whether submission occurred (null/unknown).
Test writer counts 1/1/1/0/0 and controller two-round totals 1 or 2, under
existing audit eligibility/opt-out/ownership rules. This does not invalidate
or rewrite historical uncertain rows. Alternative rejected: nullable attempt
on a new inference row when submission is unknown (asserts an unproved call).

## R8 — Governance, AVM and provisioning gates

**Decision**: Gate future Bicep authoring on current target-scope
`04-governance-constraints.md` and `.json`, live inherited-policy discovery and
Portal parity. Do not create assumed governance artifacts here. Verify a
published AVM version/composition before touching raw deployment resources.
Limit conversion to affected deployment composition if parity can be proven;
otherwise stop for a scope decision.

**Rationale**: Prior pairs exist under specs 001/003/006/007/008; the inspected
008 pair's Markdown declares inheritance/parity unverified and its subscription
differs from dev parameters. It cannot clear 041. Repository instructions
mandate AVM where available. Official upstream account AVM supports AIServices,
and its deployment child source supports an existing parent, model, SKU, RAI
policy and version-upgrade option. Source presence does not establish a
published consumable child version or no-op equivalence.

**Alternatives considered**: Treat historic zero-assignment queries as clearance
(incomplete); use baseline tags as policy (not authoritative); exempt raw Bicep
because it pre-exists (not permitted); rewrite the whole account/platform to
adopt AVM (unapproved scope expansion).

**Public reference checked, 2026-10-18**:
- [AVM account source](https://github.com/Azure/bicep-registry-modules/blob/main/avm/res/cognitive-services/account/main.bicep)
- [AVM deployment child source](https://github.com/Azure/bicep-registry-modules/blob/main/avm/res/cognitive-services/account/deployment/main.bicep)

AVM defaults, including capacity and version upgrade behaviour, must not
override approved selections. Preserve serialized child deployment/RAI
operations to avoid account operation conflicts. Build generated ARM from
Bicep; no hand editing.

**Authority refinement (I1)**: Recorded scoped G0 approval permits baseline/
governance reads before that evidence exists. Once baseline/governance/AVM
and local candidate gates pass, an explicit G0 validation scope permits
target metadata/mandatory What-If/carve-out evidence collection for G4.
G4 separately authorises specified release stages; neither generic read
credentials nor this plan permits canary/activation/switch/promotion.
Requiring G4 evidence before allowing its collection was circular and is
rejected; required What-If and no implicit Azure authority are preserved.

**Evidence-validity refinement (U3)**: Use an approved target freshness/
invalidation policy/version with timestamps and scope plus image/config/
compiled-proposal revision bindings. Define window/invalidation/recollection
rules there, not a universal duration. Missing policy, missing binding or
unevaluated drift fails readiness and affected authoring gates closed. A
previously approved baseline needs explicit reconciliation to a new candidate;
refresh needs G0 and does not itself authorise release.

## R9 — Later migration and validation scope

**Decision**: P1 preserves deployment resources; P2 is independent opt-in.
Require replacement quota headroom for concurrent old/new allocations under
the correct region/model/SKU quota pool, policy/RAI/RBAC readiness, verified
model equivalence, paired revision switch, forward/rollback checks and separate
retirement approval. Existing capacity isolation is not proof of unlimited
account/global quota.

**Acceptance refinement (I3)**: Report three levels: local implementation/
procedure verification, target P1 release readiness, and separately approved
real P2 operational migration acceptance. Synthetic tabletop results cover
procedure branches only, not SC-006 actual replacement/switch/rollback
acceptance or operational authority. Actual P2 remains optional and externally
pending; P1 may retain current identities indefinitely.

**Rationale**: A deployment rename is a new resource identity, not a metadata
edit. Keeping old resources is necessary but insufficient: rollback also needs
compatible image/configuration and available capacity.

**Alternatives considered**: Delete old resources first (no rollback); automatic
retirement after switch (not authorised); assume dev quota/settings apply
universally (unsafe).

**Validation baseline**: `uv run --no-sync python -m pytest tests/contract/test_foundry_chat_client_aoai.py -q -p no:cacheprovider`
passed **10 tests** on the unchanged code. These tests explicitly include
first-write-wins and do not catch dispatcher/MAF failures. Replace that assertion
with strict-conflict acceptance and add scoped regression cases, not broad
tool or dependency churn.
