## Summary

Separate operational tier, Azure deployment name, model identifier and model
version. Introduce one shared, immutable chat-routing configuration/resolution
contract used by common LLM clients, MAF, the simulation controller and the
simulation dispatcher. Explicit tier deployments are authoritative; simulation
requires its explicit deployment and never resolves through a live-tier fallback.
Reject conflicting routing keys instead of first/last-write-wins selection.

Expose independent selections through top-level Bicep and publish separate
per-tier identity metadata. Preserve each environment's approved existing
deployments, models, versions and protections in the P1 rollout. Publish a
collision-free compatibility CSV that retains embedding consumers and
unambiguous legacy model-key lookup. Deliver strict code and its cleaned
configuration as a matched revision, not strict code against today's ambiguous
environment.

Audit the resolved identity and actual inference attempt, including failures,
without changing historical records. Document a separately approved P2 naming
migration, with quota/policy checks, replacement readiness, revision switching,
rollback and independent retirement approval.

## Design and rollout ordering

1. **Evidence prerequisite**: reconcile each target's approved deployment
   baseline and policy scope. Dev observations are not deployment parameters.
   G0 separately authorises scoped read-only collection before G1/G2 evidence
   exists, then explicitly scoped target validation (including required
   What-If) after G1–G3/local candidate review to assemble G4 evidence.
   Collection approval never authorises canary/activation/switch/promotion.
   Evidence must satisfy an approved freshness/invalidation policy and bind
   target plus exact image/config/compiled-proposal revisions; missing policy
   or bindings fail closed, without an invented universal TTL.
2. **Producer/contract preparation**: plan collision-free tier aliases plus
   retained unambiguous model/embedding keys, independent model metadata, and
   reader-first additive provenance schema compatibility.
3. **Matched candidate revisions**: assemble corrected application image and
   cleaned routing environment together. Validate the exact candidate snapshot
   offline before activating strict conflict rejection. Never release strict
   readers into the old ambiguous CSV or depend on a temporary first-write-wins
   bypass. Existing active revisions retain their own snapshot until switch.
4. **P1 initial switch**: after approvals, use existing deployment identities
   and models; route canary requests for common, MAF, controller and dispatcher;
   verify audit and streaming; switch only to a passing revision pair. Retain
   safe rollback image/configuration and resources.
5. **P2 optional migration**: separate approval, verified model-equivalent
   purpose-named replacements, quota headroom and policy checks, candidate
   revision switch, verification and rollback. Retire only after another
   explicit approval. Initial rollout does not create replacements.

The detailed release contract is
[contracts/rollout-and-preflight.md](contracts/rollout-and-preflight.md).
This ordering describes later authorised work, not actions executed now.
