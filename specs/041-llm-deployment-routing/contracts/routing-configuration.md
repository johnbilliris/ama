# Contract: Tier Configuration and Runtime Resolution

> Generated by SpecKit planning agent | 2026-10-18

## Scope

Internal configuration/API contract for FR-001–FR-003 and FR-005–FR-012.
Preserve public chat/SSE behaviour, SDK transport parameters, AAD and safety
controls. This document specifies future behaviour, not implemented code.

## Environment contract

| Setting | Meaning / rule |
| --- | --- |
| `AZURE_AI_PROJECT_ENDPOINT` | Existing Foundry/AIServices endpoint; required for affected production inference |
| `AZURE_AI_PROJECT_REGION` | Existing approved region; retain gateway enforcement |
| `AZURE_AI_<TIER>_DEPLOYMENT` | Authoritative resource name, with TIER = REASONING/DRAFTING/SIMULATION |
| `AZURE_AI_<TIER>_MODEL_ID` | Underlying model identifier, separate from deployment |
| `AZURE_AI_<TIER>_MODEL_VERSION` | Underlying model version, separate from API version |
| `AZURE_AI_<TIER>_MODEL_KEY` | Retained derived `model_id@model_version`; compatibility/metadata, not tier selection |
| `AZURE_AI_PROJECT_DEPLOYMENTS` | Validated compatibility CSV, not the identity authority for explicit tier routing |
| `EMBEDDING_DEPLOYMENT_NAME` | Existing direct query embedding configuration; unchanged |

New generated settings contain complete tier identity metadata. Do not
introduce a global model-version fallback. Legacy configurations can lack all
new identity fields; unavailable identity is audited explicitly. A partial
pair, empty supplied field or inconsistency with supplied MODEL_KEY is a
configuration error. Legacy exact `model@version` can supply metadata only
when its association with the resolved deployment/account is proven, as below;
a unique key alone is insufficient. Bare model keys do not invent a version.

## Compatibility CSV grammar and validity

```text
mapping := entry ("," entry)*
entry   := routing-key "=" deployment-name
```

Surrounding whitespace is trimmed. An absent/blank entire map is allowed for a
fully explicit chat path; a required legacy lookup without a map fails.
Non-empty maps must contain non-empty entries, keys and values with one `=`;
reject malformed entries rather than silently discard them. Repeated identical
pairs are idempotent. One key designating two different names fails with both
destinations and the key in the diagnostic, regardless of ordering.

New output:
- Includes `reasoning`, `drafting`, `simulation` alias entries.
- Includes exact model/version keys only when all occurrences of that key
  point to one unique deployment; shared chat model keys are omitted.
- Retains existing unambiguous legacy base-model keys when explicitly
  configured/needed; does not generate speculative aliases.
- Includes the unchanged embedding model/version key and deployment.
- Never replaces a collision with an arbitrary first or last entry.

Synthetic routing example (not approved Azure model parameters):

```text
reasoning=existing-r,drafting=existing-d,simulation=existing-s,text-embedding-3-large@1=existing-e
```

All three chat deployments may host the same model/version, supplied separately
through metadata. That shared coordinate is intentionally absent from this CSV.
Eval/non-tier clients requiring it must receive a deliberately selected,
unambiguous per-run model mapping, not infer a tier.

## Resolution precedence

Validate requested purpose, required values, metadata consistency and any
supplied raw map before dispatch. Reject conflicts even if an explicit tier
would otherwise resolve. Resolve without network I/O:

1. For tier-based requests, a present non-empty explicit tier deployment wins
   over any valid map alias or valid legacy mapping.
2. A present-but-empty explicit tier is invalid; do not interpret it as
   permission to fall back.
3. Simulation without its explicit deployment fails. Neither a `simulation`
   CSV alias nor simulation/reasoning model keys permit fallback.
4. Reasoning/drafting with absent explicit settings may use a valid tier alias
   in the map, then the configured tier's unambiguous legacy exact model key,
   then an explicitly configured unambiguous base key.
5. A non-tier legacy caller may use exact key then unambiguous configured base
   key. It must not guess a tier when a shared key has been omitted.
6. No match, unsupported tier or missing required endpoint/region produces an
   actionable configuration error before inference, not GPT-4o/model defaults.

Only chat purposes are accepted by the chat-tier API. Keep existing embedding
lookup separately supported; do not pass embedding through chat-tier validation.
Validate simulation isolation against the **effective resolved** reasoning and
drafting destinations in the same account/endpoint snapshot, not only explicit
live-tier env values. Resolve each configured live path by the same precedence:
explicit, alias, exact coordinate, configured base key. An equal deployment
name within that account fails before simulation dispatch, even when both live
explicit settings are absent. An unresolved required live comparison fails
closed on the affected simulation path; do not guess a different account or
declare isolation from absent env settings. Unrelated paths remain path-local.

### Metadata association after destination resolution

Choose the destination first. New complete tier identity fields describe that
configured destination and remain subject to target preflight verification.
With those fields absent, an exact legacy coordinate may supply identity only
if the validated snapshot maps that coordinate to the **same resolved
deployment in the same account**, or a target/config-bound verification
reference proves that association. A unique `model@version -> B` entry cannot
describe explicit deployment A (nor alias-selected A). Keep A as destination
and model identity unavailable (`metadata_source=unavailable`); do not borrow
B's metadata, reroute to B, or fail merely because optional legacy identity
cannot be associated. Bare-key-only resolution can supply model_id when the
same association is proven, but never invents model_version.

Required tests include explicit A with new identity fields absent and exact
legacy coordinate pointing to B (unavailable identity), matching A (associated
legacy identity), absent association (unavailable), and cross-account evidence
(not accepted). Isolation tests include explicit simulation S versus each live
alias/exact/base path resolving to S with no live explicit env settings, plus
mixed explicit/legacy reasoning/drafting and distinct-destination controls.

## Client adapter obligations

| Consumer | Obligation |
| --- | --- |
| `LLMClientConfig` | Capture full env snapshot; expose one resolved deployment/identity result; no new live env reads during selection |
| `LLMClient` / `LiveFoundryChatClient` | Use shared result; explicit tier before valid map entries; preserve `model_key=` seam for legacy/test callers |
| MAF factory | Same result, no requirement to duplicate tier aliases in CSV; preserve factory arguments and managed-identity token provider |
| Controller | Explicit simulation only before any completion; retain direct OpenAI streaming/tools transport |
| Dispatcher | Every role requests simulation, never reasoning/model-key fallback; resolve destination from canonical result |
| Ingest/eval parser | Same strict map validity; retain separate package imports and contract parity tests |
| Query embedding | Preserve existing direct deployment env and expected dimensions |

The test-only `AZURE_OPENAI_*` path remains hermetic and cannot become a
production fallback when Foundry configuration is invalid. Constructor-injected
maps are validated for non-empty keys/values; duplicate conflict tests must
exercise raw CSV because Python dictionaries have already lost duplicates.

## Error contract

Common transports use `FoundryConfigurationError`; MAF retains its externally
observed `ValueError` factory boundary with the shared diagnostic as its cause.
Controller retains existing SSE `error` events and `openai_unavailable` for
configuration errors, naming the actual missing `AZURE_AI_SIMULATION_DEPLOYMENT`
when appropriate. Dispatcher uses its existing Foundry error logging and
marked degraded reply, augmented with explicit configuration error provenance;
readiness must not report ready on unresolved routing.

Required diagnostics identify tier, missing/invalid setting or conflicting key
and destinations; no secrets, prompt bodies or tenant PII. Config errors do not
become transport retries. API adapters preserve existing HTTP error/degradation
conventions and must not convert a configuration failure into a claimed model
call. Unrelated application paths need not fail at startup.
